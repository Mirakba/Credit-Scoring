# Кредитный скоринг: сбор таргета, фичи и модель PD

Ноутбук `Untitled-1.ipynb` решает учебную задачу построения скоринговой модели для потребительских кредитов (суммы в узбекских сумах, UZS). Работа проходит полный путь: загрузка данных из PostgreSQL, разведка таблиц, сборка таргета без готовой разметки, анализ динамики просрочки, генерация признаков строго на момент решения, обучение нескольких моделей и выбор порога отсечения.

## Структура ноутбука

| Шаг | Что делается |
|---|---|
| Подключение | Подключение к БД `academy_db` через SQLAlchemy, загрузка всех `scoring_`-таблиц |
| Шаг 1. Постановка задачи | Пять вопросов о бизнес-решении, событии, популяции, данных и критерии приёмки *(ячейка с ответами пока пустая)* |
| Шаг 2. Разведка данных | Пропуски стажа по каналам и годам, статусы договоров, просмотр таблиц *(сводная таблица источников пока не заполнена)* |
| Шаг 3. Сбор таргета | SQL-запрос, считающий просрочку по графику платежей в горизонте 6 месяцев |
| Шаг 4. Анализ проблемы | Bad rate по месяцам, сравнение одобренных и отклонённых, аномалии в анкете |
| Шаг 5. Фичи | Анкета, бюро (as-of join), карточное поведение и диспуты за 6 месяцев, текущая долговая нагрузка |
| Data Cleaning | Заполнение пропусков, удаление колонок с утечкой |
| Моделирование | LogReg, Random Forest, XGBoost, LightGBM с подбором гиперпараметров на `TimeSeriesSplit` |
| Оценка | ROC-AUC, Gini, PR-AUC, подбор порога, важность признаков, анализ `decline_rate` |

## Данные

Источник: PostgreSQL, база `academy_db`.

| Таблица | Сущность | Ключ | Строк |
|---|---|---|---|
| `scoring_applications` | Заявка на кредит | `application_id` | 18 000 |
| `scoring_applications_full` | Заявка + текущий статус договора | `application_id` | 11 277 |
| `scoring_bureau_snapshots` | Снимок кредитного бюро | `client_id` + `snapshot_date` | 86 161 |
| `scoring_card_transactions` | Карточная транзакция | `txn_id` | 1 044 743 |
| `scoring_card_disputes` | Диспут по транзакции | `dispute_id` | ~2 470 |
| `scoring_contracts` | Выданный договор | `contract_id` | ~11 280 |
| `scoring_payments` | Плановый и фактический платёж | `contract_id` + `due_date` | — |

Таблица `scoring_applications_full` в признаки не идёт: колонки `contract_status_now` и `dpd_max` описывают состояние договора уже после выдачи и являются утечкой из будущего.

## Определение таргета

Дата среза (`as_of_date`) — **2025-04-30**, горизонт наблюдения — **6 месяцев** с даты выдачи.

Заявка считается **bad (target = 1)**, если:

- максимальная просрочка (`max_dpd_6m`) по платежам, назначенным в первые 6 месяцев, составила **90 дней и более**;
- либо заявка была **отклонена** (`final_decision = 'rejected'`).

Краевые случаи:

- неоплаченный платёж считается просроченным до `min(as_of_date, issue_date + 6 мес.)`;
- досрочные платежи дают просрочку 0 (через `GREATEST(..., 0)`);
- в выборку попадают только «зрелые» заявки с `decision_date <= 2024-10-31`, у которых окно наблюдения уже закрылось.

Итог: 13 189 заявок, из них 7 411 good и 5 778 bad.

## Основные наблюдения

Доля bad по месяцам решения держалась в диапазоне 39–45% с июня 2023 по июль 2024, а в августе–октябре 2024 выросла до 47–49%.

Одобренные клиенты заметно отличаются от отклонённых: медианный заявленный доход 8,2 млн против 3,8 млн UZS, медианная запрошенная сумма 10,8 млн против 6,4 млн UZS. Стаж у групп практически одинаковый. Старая политика почти полностью совпадает с итоговым решением (около 95% совпадений).

Пропуски стажа (`employment_months`) составляют около 7–8% и равномерно распределены по каналам и годам.

`decline_rate` (доля отклонённых карточных операций) монотонно связан с риском: в нижнем дециле bad rate около 19%, в верхнем около 58%.

## Признаки

Все признаки считаются только по данным, доступным до `decision_date`.

**Анкета:** `channel`, `purpose`, `requested_amount_uzs`, `term_months`, `declared_income_uzs`, `employment_months`, `employment_missing`.

**Бюро** (последний снимок с `snapshot_date <= decision_date`, через `pd.merge_asof(direction="backward")`): `existing_debt_uzs`, `active_loans_cnt`.

**Карты за 6 месяцев до заявки:** `txn_cnt`, `avg_salary`, `purchase_sum`, `purchase_cnt`, `avg_purchase_per_month`, `decline_rate`, `decline_cnt`, `salary_to_declared` (подтверждение заявленного дохода зарплатой), `remainder` (зарплата минус траты).

**Диспуты за 6 месяцев:** `dispute_cnt_6m`, `dispute_amount_6m`, `fraud_claim_cnt_6m`.

**Долговая нагрузка по прошлым договорам банка:** `existing_monthly_payment`, `contract_cnt`, `total_debt`, а также `monthly_payment_uzs` (для заявок без договора рассчитан как аннуитет по средней ставке года).

Обработка пропусков: стаж восстанавливается из предыдущих заявок клиента (последнее известное значение плюс прошедшие месяцы), остаток заполняется медианой; признаки бюро и карт заполняются нулём для клиентов без истории.

Исключены как утечка или служебные: `final_decision`, `approved_by_old_policy`, `max_dpd_6m`, `late_days_6m`, `late_payments_6m`, `issue_date`, `snapshot_date`, `year`, `avg_rate`, `active_months`, `bureau_score`.

## Разбиение и модели

Разбиение по времени:

- **train:** `decision_date < 2024-07-30`
- **valid:** `2024-07-30 <= decision_date < 2024-09-30` (1 559 заявок)
- **test:** `decision_date >= 2024-09-30` (783 заявки)

Подбор гиперпараметров на train с `TimeSeriesSplit(n_splits=5)`, метрика ROC-AUC.

| Модель | CV ROC-AUC | Valid ROC-AUC | Test ROC-AUC |
|---|---|---|---|
| Random Forest | 0.744 | — | — |
| XGBoost | 0.817 | 0.846 | 0.821 |
| **LightGBM (финальная)** | 0.827 | **0.841** | **0.824** |

Финальная модель — LightGBM с усиленной регуляризацией (`num_leaves=7`, `reg_alpha=9`, `reg_lambda=35`) и early stopping по валидации. Разрыв train/valid по AUC около 0.056. Gini на тесте около 0.64.

**Порог.** На валидации порог перебирался от 0.10 до 0.90; выбран **0.35** как баланс precision и recall (F1 ≈ 0.77). На тесте при этом пороге: precision для bad около 0.72, recall около 0.79.

Самые важные признаки LightGBM (по числу сплитов): `requested_amount_uzs`, `monthly_payment_uzs`, `term_months`, `employment_months`, `declared_income_uzs`, `existing_debt_uzs`, `decline_rate`.

## Известные ограничения

Отклонённые заявки получают `target = 1` по определению. Поэтому модель во многом учится воспроизводить прошлую политику одобрения, а не только реальный дефолт; это видно по bad rate 96% у заявок, отклонённых старой политикой. Стоит отдельно проверить модель только на одобренных заявках с реальной просрочкой или применить reject inference.

`monthly_payment_uzs` для одобренных берётся из фактического договора, а для отклонённых рассчитывается по формуле. Источник значения косвенно совпадает с решением, а значит и с таргетом, поэтому признак может содержать утечку. Надёжнее считать платёж по формуле для всех заявок.

В ячейке проверки порога стоит `thr = 0.`; для воспроизведения результатов нужно заменить на `0.35`.

## Запуск

Требования: Python 3.13 (проверено в Anaconda), доступ к базе.

```bash
pip install pandas sqlalchemy psycopg2-binary scikit-learn xgboost lightgbm matplotlib seaborn python-dateutil
```

В первой ячейке заполните `username` и `password`. Учётные данные лучше не хранить в ноутбуке, а читать из переменных окружения:

```python
import os
username = os.environ["DB_USER"]
password = quote_plus(os.environ["DB_PASSWORD"])
```

Ноутбук выполняется сверху вниз. Таблица транзакций занимает около 70 МБ в памяти, а подбор гиперпараметров (до 750 обучений) может занять заметное время.
